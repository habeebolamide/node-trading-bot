# Phase 8 security and execution-boundary review

Scope: local PAPER milestone, Express bearer API, four native services, PostgreSQL ownership/fencing/ledger guards, notification transport, deployment and recovery tools. This is a code/test review, not an independent penetration test or authorization for LIVE execution.

| Boundary               | Control and evidence                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication         | 256-bit opaque tokens, SHA-256 hashes only, expiry/revocation checked per request, no query-string/cookie authentication. Existing PostgreSQL foundation tests plus token CLI issuance/revocation tests cover valid, revoked and viewer access.                                                                                                                                                                                    |
| Authorization          | OWNER mutations; VIEWER reads; account-scoped 404s; validated UUIDs, strict payload schemas, idempotent durable commands and configuration version checks. API DB role cannot issue tokens, truncate tables or migrate.                                                                                                                                                                                                            |
| Browser transport      | Production API binds loopback behind Caddy TLS; only loopback forwarding headers are trusted; no permissive CORS; explicit Authorization headers avoid ambient-cookie CSRF. Authenticated API responses use no-store. Header/request timeouts and the existing per-IP rate limit bound request work. SSE is bounded to one minute and reconnects through authentication.                                                           |
| Secrets and logs       | Private environment files outside releases, independent database logins, notifier-only Telegram secret, private output token files, redacted bearer/nested credentials and sanitized network errors. Security scanner rejects tracked env/private-key/dump artifacts, likely hard-coded Telegram tokens and direct authenticated exchange endpoints. It is a narrow regression check, not a general secret-scanning certification. |
| Service privileges     | Non-login group roles with explicit DML grants; no service DELETE/TRUNCATE/DDL/token-issuance privileges. Public schema creation and database TEMP are revoked to prevent object-shadowing attacks. Restricted-role restore rehearsal runs a real API bot creation, replay and notification dispatch; negative tests reject worker writes to forward state, notifier financial updates, runtime token reads and API deletes.       |
| Economic isolation     | Database guards restrict worker economic/configuration/control/evaluation writes to run-specific replay accounts, and runtime writes to FORWARD accounts. Existing coin exclusivity, immutable evaluations/config/ledger, reservation locks and database-time fencing remain active. Compromised service credentials are still trusted within their granted scope; no service login may inherit an administrative role.            |
| Failure policy         | Production defaults to Protect & Freeze. Pending entry remainders cancel; filled exposure remains protected and managed. The entry gate is checked again inside the intent transaction after asynchronous evaluation persistence. Database submission failure cannot bypass durable intent or clear exposure. Unknown historical ordering remains uncertain.                                                                       |
| Notification isolation | No strategy/risk/runtime dependency on Telegram; dedicated process and small pool, hard deadline, bounded attempts, durable dedupe/leases. High-CPU replay plus hanging Telegram regression completes forward PAPER fills/protection/closure independently. Acknowledgment never clears an incident or resumes entries.                                                                                                            |
| Database evolution     | One physical connection holds the migration advisory lock; every applied timestamp/hash must match the exact source prefix. Pending migrations run transactionally; injected bad DDL leaves no table or journal advancement. No applied migration is rewritten.                                                                                                                                                                    |

Corrupt archives and nonempty targets are refused. No password appears in utility arguments. ## Remaining deployment obligations

The operator must provision TLS/DNS, private PostgreSQL/SCRAM accounts, exact group membership, firewall rules, supported Linux cgroups, host monitoring, encrypted off-host backups, retention and measured restore/RPO procedures. The repository supplies systemd/Caddy/CI configuration and a local native restore rehearsal; the current macOS host cannot prove Linux cgroup behavior, external certificates, a remote CI execution or a multi-day public-feed soak. Treat these as host acceptance checks before exposing a paper deployment.

Financial integrity depends on PostgreSQL and the trusted migration/restore administrator. Superusers can bypass triggers; backups from an untrusted administrator are not authenticated by their self-supplied checksum. Read-only dashboard analytics can still be expensive at very large history sizes, and a shared PostgreSQL host can suffer global resource pressure. Measure market counts, replay volume, connection capacity and query latency on the target host; stop background work before compromising position monitoring. The combined replay/Telegram process load test is a regression bound, not a capacity guarantee.
